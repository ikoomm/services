## Post 1: deciding what belongs in an MVP

Before you price an MVP, describe what its first user needs to finish.

For a booking product, that might mean finding a time, reserving it and getting a confirmation. A referral program can probably wait. Handling a slot that has just been taken probably can't.

That distinction makes the scope easier to discuss. You can trace each feature back to a task, then ask what would happen if you left it out.

At Early, product definition comes before development: the target user, core problem and primary use case shape the build. A clickable design gives you a chance to work through those decisions before committing to code.

Try describing your first release as a task someone can complete. Which feature suddenly looks optional?

## Post 2: turning a spreadsheet into a useful brief

Before replacing a spreadsheet, watch somebody use it.

Ask them to follow one order from the first enquiry to the final update. Notice where they copy a value, ask a colleague for permission or switch to a second file. Have them show you what happens when an order changes halfway through.

Those details belong in the software brief. So do the formulas that still work well. Rebuilding a process is a good time to question it, but the useful parts deserve to survive.

Early builds internal tools around how a business operates, including the calculations and workflows its team already relies on.

For your next scoping session, bring a real example with sensitive details removed. Include the awkward exception you usually explain out loud.

## Post 3: evaluating an AI-assisted software partner

If a studio uses AI to build your software, ask who signs off on the work.

It's a practical question. A generated function can look convincing while handling a missing value badly or giving the wrong person access. Ask to see how the team checks those cases and who owns the decision to release.

Early's published approach puts architectural decisions and code review with its developers. AI helps with implementation; the team remains responsible for what ships.

Then ask about the handover. You should know who will control the repository and infrastructure, and what documentation you'll receive. Early includes those in its handoff.

A useful conversation with a development partner gets specific about review, release and ownership. You should leave knowing who to call when something needs fixing.

## Five-slide carousel: does this feature belong in version one?

### Slide 1

**Does this feature belong in version one?**

Test it against the first thing a user needs to finish.

### Slide 2

**Write down the task**

For a booking product: choose an available time, reserve it and receive confirmation.

Now you have something specific to scope.

### Slide 3

**Try removing the feature**

Can the user still finish?

A referral program might wait. Preventing two people from taking the same slot belongs in the booking flow.

### Slide 4

**Walk through the awkward case**

The slot disappears before confirmation. What does the user see next?

Put that path in the clickable design before development starts.

### Slide 5

**Give each feature a reason**

Keep it when it enables the task or prevents a defined failure.

Park the rest with a reason to revisit it. Bring that list to your scoping conversation.
